## 2. 목표와 검증 기준

**검증할 가설:** "AI 스터디 모임을 열면, 실제로 신청하고 출석하는 사람이 있다."

| 지표 | 정의 | 검증 통과 기준 (제안값) |
|------|------|-------------------|
| 모임당 신청 수 | 모임 하나에 신청한 멤버 수 | 평균 5명 이상 |
| 출석률 | 출석 체크된 인원 ÷ 신청 인원 | 60% 이상 |
| 재신청률 | 두 번째 모임에도 신청한 멤버 비율 | 40% 이상 |

- 측정 기간: 테스트 서버 오픈 후 4주, 모임 3회 이상.
- 기준값은 제안값이에요. 오픈 전에 운영자가 확정해요.
- 지표는 별도 분석 도구 없이 DB에서 바로 집계해요 (관리자 화면에 표시).

## 3. 범위

### v0에 포함
1. **모임 목록**: 다가오는 모임과 지난 모임을 일정순으로 보여 줘요.
2. **모임 상세**: 주제, 일시, 장소(온라인 링크 또는 오프라인 주소), 정원, 현재 신청 인원, 설명.
3. **신청 / 신청 취소**: 정원이 차면 대기자로 등록되고, 취소가 생기면 대기 1순위가 자동으로 확정돼요.
4. **내 신청 내역**: 내가 신청한 모임과 상태(확정·대기·취소)를 보여 줘요.
5. **운영자 화면**: 모임 생성·수정·마감, 신청자 명단, 출석 체크, 2장의 지표 3개.
6. **캘린더 추가**: 모임 상세에서 `.ics` 파일을 내려받아요 (외부 API 없이 구현).

### v0에서 제외 (이후 버전)
- 게시판·자료 공유, 주간 AI 트렌드 다이제스트, 멤버 프로필·매칭
- 알림(이메일·카카오 알림톡·푸시). v0에서는 운영자가 기존 채널(오픈채팅 등)로 직접 공지해요.
- 결제·유료 모임, AI 기능(Claude API), 실서비스 배포·도메인

## 4. 기술 구현

### 스택
| 영역 | 선택 | 이유 |
|------|------|------|
| 프레임워크 | Next.js (App Router) + TypeScript | 화면과 API를 한 프로젝트에 두고, 관례가 뚜렷해서 Claude가 유지보수하기 쉬워요 |
| DB | SQLite + Prisma | 테스트 서버에서는 파일 하나로 끝나요. 나중에 Postgres로 옮길 때 Prisma provider만 바꾸면 돼요 |
| 스타일 | CSS Modules + 디자인 토큰 | `aisync.html`의 색상 토큰과 다크 모드 패턴을 그대로 옮겨요 |
| 테스트 | Vitest(로직·API) + Playwright(신청 흐름 E2E) | CLAUDE.md의 "코드 변경엔 테스트" 규칙을 지키기 위함 |
| 실행 | `npm run dev` (로컬), 테스트 서버는 `npm run build && npm start` | 배포 인프라는 v0 범위가 아니에요 |

### 데이터 모델
```
User        id, name, email?, role(member|admin), createdAt
Meetup      id, title, description, startsAt, endsAt, location, onlineUrl?,
            capacity, status(open|closed|canceled), createdAt
Application id, userId, meetupId, status(confirmed|waitlisted|canceled),
            attended(bool), createdAt, canceledAt?
            UNIQUE(userId, meetupId)
```

### 핵심 규칙 (테스트로 반드시 고정할 것)
- 신청 시 `confirmed` 인원이 정원 미만이면 `confirmed`, 아니면 `waitlisted`.
- `confirmed` 신청이 취소되면, 가장 먼저 대기한 `waitlisted` 한 명을 `confirmed`로 올려요. 이 작업은 **한 트랜잭션** 안에서 처리해 동시 신청 시 정원 초과를 막아요.
- 같은 모임에 중복 신청은 불가(UNIQUE). 취소 후 재신청하면 기존 행을 되살리고 대기 순서는 맨 뒤로 가요.
- 마감(`closed`)이나 취소(`canceled`)된 모임, 시작 시각이 지난 모임에는 신청할 수 없어요.
- 시간은 DB에 UTC로 저장하고, 화면에서는 Asia/Seoul로 보여 줘요.

### 인증 (가입 흐름 미정에 대한 대응)
- 인증은 `getCurrentUser()` 하나로 감싸서, 나중에 방식만 바꿔 끼울 수 있게 해요.
- v0 테스트 서버에서는 **이름 + 이메일 간이 가입**(비밀번호 없음, 세션 쿠키)을 써요. 운영자 계정은 시드 데이터로 만들어요.
- 이 방식은 신원 확인이 되지 않으므로 테스트 서버 전용이에요. 실서비스로 가기 전에 9장의 결정이 필요해요.

## 5. 화면과 UX

| 경로 | 화면 | 핵심 UX |
|------|------|--------|
| `/` | 랜딩 + 다가오는 모임 3개 | 기존 랜딩 문구를 재사용하고, CTA는 `#apply` 대신 `/meetups`로 연결 |
| `/meetups` | 모임 목록 | 카드에 "잔여 n석" 또는 "대기 n명"을 크게 보여 줘서 신청을 유도 |
| `/meetups/[id]` | 모임 상세 | 하단 고정 신청 버튼(모바일). 상태에 따라 "신청하기 / 대기 신청 / 신청 취소 / 마감" |
| `/me` | 내 신청 내역 | 확정·대기 상태와 대기 순번을 보여 줘요 |
| `/admin` | 운영자 대시보드 | 지표 3개, 모임 관리, 신청자 명단, 출석 체크 |

- 로그인 없이도 목록과 상세는 볼 수 있어요. 신청 버튼을 누르는 순간에 간이 가입을 요청해요.
- 모바일 기준(375px)에서 좌우 여백 16px, 가로 스크롤 없음. 라이트·다크 모드를 모두 지원해요.
- 신청 직후에는 확정인지 대기인지 결과를 바로 보여 주고, 캘린더 추가 버튼을 함께 노출해요.

## 6. 우려사항과 대응

| 우려 | 영향 | 대응 |
|------|------|------|
| 초기 사용자가 없음 (콜드 스타트) | 빈 목록이 "죽은 서비스"처럼 보여요 | 오픈 전에 운영자가 모임 2~3개를 미리 등록하고, 기존 채널로 첫 멤버를 직접 초대 |
| 노쇼 | 출석률 지표가 왜곡돼요 | 출석 체크를 운영자 화면에 넣어 지표로 직접 측정. 제재 기능은 v0에서 만들지 않음 |
| 간이 가입의 신원 미확인 | 남의 이메일로 신청 가능 | 테스트 서버 범위로만 운영, 실서비스 전 인증 교체 |
| 개인정보 | 이름·이메일을 저장해요 | 수집 항목을 최소화하고, 가입 화면에 수집 목적을 명시. 테스트 종료 시 데이터 삭제 기준 마련 |
| 테스트 서버의 한계 | 외부 사용자가 접속하기 어려울 수 있어요 | 9장에서 접속 방식을 결정 |

## 7. 트레이드오프 기록

- **SQLite vs 관리형 Postgres(Supabase 등)**: 테스트 서버에서는 설정이 없는 SQLite를 택했어요. 대신 동시 쓰기 성능과 백업은 약해요. 실서비스 전환 시 Postgres로 옮겨요.
- **간이 가입 vs 소셜 로그인**: 가입 흐름이 미정이라 가장 바꾸기 쉬운 쪽을 택했어요. 대신 신원 보장이 없어요.
- **알림 기능 제외**: 개발 범위를 크게 줄이는 대신 운영자가 수동으로 공지해야 해요. 수요가 검증되면 가장 먼저 추가할 후보예요.
- **기능 1개만**: 검증 신호가 선명해지는 대신, 커뮤니티로서 머무를 이유(게시판 등)는 아직 없어요.

## 8. 구현 순서

1. Next.js 프로젝트 생성, 디자인 토큰 이식, Vitest·Playwright 설정
2. Prisma 스키마와 시드(운영자 1명, 샘플 모임 3개)
3. 신청·취소·대기 승격 로직과 단위 테스트 (트랜잭션 포함)
4. 모임 목록·상세·내 신청 화면
5. 간이 가입과 `getCurrentUser()`
6. 운영자 화면 (모임 관리, 출석 체크, 지표)
7. `.ics` 내보내기
8. E2E 테스트: 신청 → 정원 초과 시 대기 → 취소 시 자동 승격
9. 모바일·다크 모드 화면 확인

사전 준비: 이 PC에는 Git이 설치되어 있지 않아요. 변경 이력을 남기려면 구현 전에 Git을 설치하고 저장소를 만드는 걸 권장해요. Node는 v24가 설치되어 있어요.

## 9. 결정 필요 항목

1. **가입 흐름** (인터뷰 4번 미정): 둘러보기 후 카카오 로그인 / 로그인 필수 / 운영자 승인제 / 이메일만 중에서 선택. 실서비스 전에 꼭 정해야 해요.
2. **테스트 서버 접속 방식**: 로컬에서만 볼지, 터널(ngrok 등)이나 무료 호스팅으로 지인에게 열지.
3. **검증 기준값**: 2장의 제안값(신청 5명, 출석 60%, 재신청 40%)을 그대로 쓸지.
4. **모임 형태**: 온라인만, 오프라인만, 혼합 중에서 무엇인지에 따라 장소 입력 UI가 달라져요.
